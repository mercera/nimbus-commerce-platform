# Engineering Handbook

## Development workflow

Work proceeds in small, explicitly scoped milestones. For each milestone:

1. Architecture decisions are settled and reviewed before any code is written.
2. Before implementation, the exact set of files to be created/modified is listed with a reason for each, and implementation waits for explicit approval.
3. Implementation follows the approved plan. Any necessary deviation (a build-time necessity, a bug in the existing setup, etc.) is called out explicitly rather than made silently.
4. The solution is built and any errors are resolved before the milestone is considered done.
5. A self-review is performed against Clean Architecture, SOLID, security, naming, duplication, maintainability, and production-readiness before moving on.
6. Documentation is updated to reflect the current state — not planned or future state — and a journal entry is added.

## Notes for future developers (and future Claude Code sessions) on authentication

- **Register, Login, Refresh, Logout, and `/me` are implemented.** `AuthController` exposes `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/refresh`, `POST /api/auth/logout`, and `GET /api/auth/me`. Refresh reads the `refreshToken` cookie, hashes it, and validates it via `IRefreshTokenStore.FindByHashAsync` — checked in this order: not found → 401 (no revocation, to avoid a guessing-based DoS against real sessions); **already revoked → reuse detected**, every active token for that user is revoked via `RevokeAllActiveForUserAsync`, then 401; expired → 401, no cascade; otherwise the token is rotated atomically (`RotateAsync`: revoke old, insert new, one `SaveChangesAsync`) and a new access token is minted via `IIdentityService.GetActiveUserAsync`. Every failure path returns an identical generic 401, mirroring Login's enumeration-safe design — the response must never reveal that reuse detection fired.
- **`IIdentityService.ValidateCredentialsAsync` is the only credential-check entry point.** `CheckPasswordAsync`/`GetUserIdAsync` (Milestone 1's original two-call shape) were removed and replaced with this single method specifically to stop Login from being able to distinguish "no such account" from "wrong password" through its own control flow. A residual timing difference still exists one layer down, inside `IdentityService` itself (it short-circuits before hashing on an unknown/inactive account) — see `Architecture.md`'s "Known limitations". Don't reintroduce a two-call lookup-then-check pattern for credential validation without re-reading that section.
- **`ApplicationUser.IsActive` is now enforced.** `ValidateCredentialsAsync` rejects inactive accounts. There is currently no code path that ever sets `IsActive` to `false` (no deactivation feature exists yet) — the field is enforced but not yet actionable from any endpoint.
- **The refresh token client-storage decision is implemented.** Login sets the refresh token as an `HttpOnly`, `Secure`, `SameSite=Strict` cookie, path-scoped to `/api/auth`, not returned in the JSON body — the wider path (rather than `/api/auth/refresh` alone) lets both `POST /api/auth/refresh` and `POST /api/auth/logout` receive the cookie. `SameSite=Strict` was chosen as the safest default for a same-site deployment — revisit before ever hosting the frontend on a different site than the API.
- **`RefreshToken`'s rotation fields (`RevokedAtUtc`, `ReplacedByTokenHash`) are live as of the Refresh milestone.** `RefreshService`/`RefreshTokenStore` set and read both. The entity's own unmapped `IsActive` computed property was deleted — it could not be translated by EF into SQL (`.Where(rt => rt.IsActive)` compiles but throws at runtime), so "active" is defined only in `RefreshService`'s state machine and in `RevokeAllActiveForUserAsync`'s hand-expanded predicate. Don't re-add a computed `IsActive` property to the entity; if a value is needed in a query, expand `RevokedAtUtc is null && ExpiresAtUtc > DateTime.UtcNow` inline so it stays translatable.
- **Known limitation: two parallel refresh requests using the same cookie can both succeed**, producing two live child tokens from one parent and an orphaned chain link (the unique index on `TokenHash` doesn't catch this, since the two new tokens are different values). If the client later retries with the now-stale cookie, reuse detection fires and revokes every session for that user — a self-inflicted lockout, not an attack. The real fix is a frontend single-flight refresh (one in-flight refresh promise, other calls queued behind it); a server-side fix would need a `RowVersion` column (new migration) or a compare-and-swap rewrite of `RotateAsync`. Deliberately not mitigated in this milestone — see `Architecture.md`, "Known limitations".
- **Reuse detection revokes every active token for the user, not just the affected chain.** There is no `TokenFamilyId`/chain-id column, only the forward-pointing `ReplacedByTokenHash` — and the parallel-refresh race above can orphan chain links, so a chain walk isn't even reliable. Revoke-all matches RFC 9700 / OAuth 2.1 BCP guidance and costs a legitimate re-login rather than risking an attacker keeping a live credential.
- **`internal sealed` for interface implementations now applies inside Application too, not just Infrastructure.** `RegisterService`/`LoginService` implement their own same-layer interfaces (`IRegisterService`/`ILoginService`) and are `internal sealed`, registered by a new `Application/DependencyInjection.AddApplication`. See `coding-standards.md`.
- **The `sub` claim does not arrive as `sub` — read `ClaimTypes.NameIdentifier`.** `TokenService` writes `new Claim(JwtRegisteredClaimNames.Sub, userId)`, but `JwtBearerOptions.MapInboundClaims` defaults to `true` and `JwtAuthenticationExtensions` does not change it, so ASP.NET's inbound map rewrites `sub` to `ClaimTypes.NameIdentifier` before the principal reaches the action. `User.FindFirstValue(JwtRegisteredClaimNames.Sub)` returns **null** and the endpoint 401s on every request — verified empirically, not inferred. `email` is likewise remapped to `ClaimTypes.Email`. Roles are unaffected: they round-trip to `ClaimTypes.Role`, which is the default `RoleClaimType`, so `User.IsInRole(...)` and `[Authorize(Roles = "...")]` work as written. Turning `MapInboundClaims` off would mean also setting `NameClaimType`/`RoleClaimType` and rewriting `TokenService`'s role claim; that was judged not worth touching working token minting for. Read `ClaimTypes.NameIdentifier` and move on.
- **`ICurrentUserService` is a use case, not an ambient "who is calling?" accessor.** It takes a `userId` parameter and returns that user's live record. There is deliberately no `ICurrentUser`/`IHttpContextAccessor` abstraction — the controller reads the claim and passes the id inward, the same way `RefreshService` receives a `userId` it did not look up. `IHttpContextAccessor` is not registered anywhere. If a future Application use case genuinely needs the caller's identity without a controller handing it over (the expected trigger is something like `CreateOrder` populating `Order.CustomerId`), introduce `ICurrentUser` *then*, and do not rename `ICurrentUserService` into it.
- **`[Authorize]` is on the `/me` action, not on `AuthController`.** Four of the five actions are intentionally anonymous — Register, Login, Refresh, and Logout — and Logout's anonymity is a deliberate security decision documented in `Architecture.md`. When protected actions come to outnumber anonymous ones, move `[Authorize]` to the controller and mark the exceptions `[AllowAnonymous]`: that default is fail-safe, since an action added without thought ends up protected rather than exposed. `BearerSecuritySchemeTransformer` already reads `IAuthorizeData`/`IAllowAnonymous` from endpoint metadata, so it keeps producing the correct OpenAPI security requirements either way — no transformer change is needed when this flips.
- **`/me` re-reads the database on every call, and that freshness is per-endpoint — not token revocation.** A deactivated user's access token stays cryptographically valid and still passes `[Authorize]`; `/me` rejects them (with `401`, not `403`) only because `GetUserProfileAsync` independently checks `IsActive`. **Any new `[Authorize]` endpoint that skips that check will serve a deactivated user for up to 15 minutes.** Don't assume `[Authorize]` alone means "this account is still in good standing".
- **The JWT signing key in `appsettings.Development.json` is a placeholder.** It must never be copied into a non-development environment.
- **`ApplicationUser` carries `FirstName`, `LastName`, `IsActive` directly** rather than in a separate profile entity — a deliberate, scoped decision for this project's size. See `Architecture.md` for the reasoning and the caveat about referencing users from Domain.
- **A migration exists (`InitialCreate`, added in Sprint 2 Milestone 2) and must be applied** with `dotnet ef database update` before Register, Login, Refresh, Logout, or `/me` can be exercised against a real database — see `development-setup.md`. No new migration was needed for the Refresh milestone (`RevokedAtUtc`, `ReplacedByTokenHash`, and both `RefreshTokens` indexes were already present in `InitialCreate`) nor for the `/me` milestone (`FirstName`, `LastName`, and `IsActive` were already columns on `AspNetUsers`).
- **Roles are wired but empty — no user can hold one.** `AddRoles<IdentityRole>()` is registered and the role tables exist in `InitialCreate`, but nothing anywhere calls `AddToRoleAsync` and there is no seeding, so `GetRolesAsync` returns an empty list for every user and `/me` always reports `"roles": []`. `[Authorize(Roles = "...")]` would therefore reject *everyone*, and cannot be meaningfully tested until role seeding exists. Build seeding first; don't add a role-protected endpoint before then.
- **No rate limiting exists yet on any auth endpoint.** `/register`, `/login`, `/refresh`, and `/logout` are all currently unthrottled and anonymous — see `Architecture.md`'s "Known limitations" and `project-journal.md` for tracking. `/me` is unthrottled too, but `[Authorize]` means an attacker must already hold a validly-signed token to reach it, so it is not exposed on the same terms.
