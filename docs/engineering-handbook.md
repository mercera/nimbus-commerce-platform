# Engineering Handbook

## Development workflow

Work proceeds in small, explicitly scoped milestones. For each milestone:

1. Architecture decisions are settled and reviewed before any code is written.
2. Before implementation, the exact set of files to be created/modified is listed with a reason for each, and implementation waits for explicit approval.
3. Implementation follows the approved plan. Any necessary deviation (a build-time necessity, a bug in the existing setup, etc.) is called out explicitly rather than made silently.
4. The solution is built and any errors are resolved before the milestone is considered done.
5. A self-review is performed against Clean Architecture, SOLID, security, naming, duplication, maintainability, and production-readiness before moving on.
6. Documentation is updated to reflect the current state — not planned or future state — and a journal entry is added.

## Notes for future developers (and future Claude Code sessions) on authentication

- **Register, Login, Refresh, Logout, and `/me` are implemented.** `AuthController` exposes `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/refresh`, `POST /api/auth/logout`, and `GET /api/auth/me`. Refresh reads the `refreshToken` cookie, hashes it, and validates it via `IRefreshTokenStore.FindByHashAsync` — checked in this order: not found → 401 (no revocation, to avoid a guessing-based DoS against real sessions); **already revoked → reuse detected**, every active token for that user is revoked via `RevokeAllActiveForUserAsync`, then 401; expired → 401, no cascade; otherwise the token is rotated atomically (`RotateAsync`: revoke old, insert new, one `SaveChangesAsync`) and a new access token is minted via `IIdentityService.GetActiveUserAsync`. Every failure path returns an identical generic 401, mirroring Login's enumeration-safe design — the response must never reveal that reuse detection fired.
- **`IIdentityService.ValidateCredentialsAsync` is the only credential-check entry point.** `CheckPasswordAsync`/`GetUserIdAsync` (Milestone 1's original two-call shape) were removed and replaced with this single method specifically to stop Login from being able to distinguish "no such account" from "wrong password" through its own control flow. A residual timing difference still exists one layer down, inside `IdentityService` itself (it short-circuits before hashing on an unknown/inactive account) — see `Architecture.md`'s "Known limitations". Don't reintroduce a two-call lookup-then-check pattern for credential validation without re-reading that section.
- **`ApplicationUser.IsActive` is now enforced.** `ValidateCredentialsAsync` rejects inactive accounts. There is currently no code path that ever sets `IsActive` to `false` (no deactivation feature exists yet) — the field is enforced but not yet actionable from any endpoint.
- **The refresh token client-storage decision is implemented.** Login sets the refresh token as an `HttpOnly`, `Secure`, `SameSite=Strict` cookie, path-scoped to `/api/auth`, not returned in the JSON body — the wider path (rather than `/api/auth/refresh` alone) lets both `POST /api/auth/refresh` and `POST /api/auth/logout` receive the cookie. `SameSite=Strict` was chosen as the safest default for a same-site deployment — revisit before ever hosting the frontend on a different site than the API.
- **`RefreshToken`'s rotation fields (`RevokedAtUtc`, `ReplacedByTokenHash`) are live as of the Refresh milestone.** `RefreshService`/`RefreshTokenStore` set and read both. The entity's own unmapped `IsActive` computed property was deleted — it could not be translated by EF into SQL (`.Where(rt => rt.IsActive)` compiles but throws at runtime), so "active" is defined only in `RefreshService`'s state machine and in `RevokeAllActiveForUserAsync`'s hand-expanded predicate. Don't re-add a computed `IsActive` property to the entity; if a value is needed in a query, expand `RevokedAtUtc is null && ExpiresAtUtc > DateTime.UtcNow` inline so it stays translatable.
- **Known limitation: two parallel refresh requests using the same cookie can both succeed**, producing two live child tokens from one parent and an orphaned chain link (the unique index on `TokenHash` doesn't catch this, since the two new tokens are different values). If the client later retries with the now-stale cookie, reuse detection fires and revokes every session for that user — a self-inflicted lockout, not an attack. The real fix is a frontend single-flight refresh (one in-flight refresh promise, other calls queued behind it); a server-side fix would need a `RowVersion` column (new migration) or a compare-and-swap rewrite of `RotateAsync`. Deliberately not mitigated in this milestone — see `Architecture.md`, "Known limitations".
- **Reuse detection revokes every active token for the user, not just the affected chain.** There is no `TokenFamilyId`/chain-id column, only the forward-pointing `ReplacedByTokenHash` — and the parallel-refresh race above can orphan chain links, so a chain walk isn't even reliable. Revoke-all matches RFC 9700 / OAuth 2.1 BCP guidance and costs a legitimate re-login rather than risking an attacker keeping a live credential.
- **`internal sealed` for interface implementations now applies inside Application too, not just Infrastructure.** `RegisterService`/`LoginService` implement their own same-layer interfaces (`IRegisterService`/`ILoginService`) and are `internal sealed`, registered by a new `Application/DependencyInjection.AddApplication`. See `coding-standards.md`.
- **The `sub` claim does not arrive as `sub` — read `ClaimTypes.NameIdentifier`.** `TokenService` writes `new Claim(JwtRegisteredClaimNames.Sub, userId)`, but `JwtBearerOptions.MapInboundClaims` defaults to `true` and `JwtAuthenticationExtensions` does not change it, so ASP.NET's inbound map rewrites `sub` to `ClaimTypes.NameIdentifier` before the principal reaches the action. `User.FindFirstValue(JwtRegisteredClaimNames.Sub)` returns **null** and the endpoint 401s on every request — verified empirically, not inferred. `email` is likewise remapped to `ClaimTypes.Email`. Roles are unaffected: they round-trip to `ClaimTypes.Role`, which is the default `RoleClaimType`, so `User.IsInRole(...)` and `[Authorize(Roles = "...")]` work as written. Turning `MapInboundClaims` off would mean also setting `NameClaimType`/`RoleClaimType` and rewriting `TokenService`'s role claim; that was judged not worth touching working token minting for. Read `ClaimTypes.NameIdentifier` and move on.
- **`ICurrentUserService` is a use case, not an ambient "who is calling?" accessor.** It takes a `userId` parameter and returns that user's live record. There is deliberately no `ICurrentUser`/`IHttpContextAccessor` abstraction — the controller reads the claim and passes the id inward, the same way `RefreshService` receives a `userId` it did not look up. `IHttpContextAccessor` is not registered anywhere. If a future Application use case genuinely needs the caller's identity without a controller handing it over (the expected trigger is something like `CreateOrder` populating `Order.CustomerId`), introduce `ICurrentUser` *then*, and do not rename `ICurrentUserService` into it.
- **`[Authorize]` is on the `/me` action, not on `AuthController`.** Four of the five actions are intentionally anonymous — Register, Login, Refresh, and Logout — and Logout's anonymity is a deliberate security decision documented in `Architecture.md`. When protected actions come to outnumber anonymous ones, move `[Authorize]` to the controller and mark the exceptions `[AllowAnonymous]`: that default is fail-safe, since an action added without thought ends up protected rather than exposed. `BearerSecuritySchemeTransformer` already reads `IAuthorizeData`/`IAllowAnonymous` from endpoint metadata, so it keeps producing the correct OpenAPI security requirements either way — no transformer change is needed when this flips.
- **`/me` re-reads the database on every call, and that freshness is per-endpoint — not token revocation.** A deactivated user's access token stays cryptographically valid and still passes `[Authorize]`; `/me` rejects them (with `401`, not `403`) only because `GetUserProfileAsync` independently checks `IsActive`. **Any new `[Authorize]` endpoint that skips that check will serve a deactivated user for up to 15 minutes.** Don't assume `[Authorize]` alone means "this account is still in good standing".
- **The JWT signing key in `appsettings.Development.json` is a placeholder.** It must never be copied into a non-development environment.
- **`ApplicationUser` carries `FirstName`, `LastName`, `IsActive` directly** rather than in a separate profile entity — a deliberate, scoped decision for this project's size. See `Architecture.md` for the reasoning and the caveat about referencing users from Domain.
- **A migration exists (`InitialCreate`, added in Sprint 2 Milestone 2) and must be applied** with `dotnet ef database update` before Register, Login, Refresh, Logout, or `/me` can be exercised against a real database — see `development-setup.md`. No new migration was needed for the Refresh milestone (`RevokedAtUtc`, `ReplacedByTokenHash`, and both `RefreshTokens` indexes were already present in `InitialCreate`) nor for the `/me` milestone (`FirstName`, `LastName`, and `IsActive` were already columns on `AspNetUsers`).
- **Roles are wired but empty — no user can hold one.** `AddRoles<IdentityRole>()` is registered and the role tables exist in `InitialCreate`, but nothing anywhere calls `AddToRoleAsync` and there is no seeding, so `GetRolesAsync` returns an empty list for every user and `/me` always reports `"roles": []`. `[Authorize(Roles = "...")]` would therefore reject *everyone*, and cannot be meaningfully tested until role seeding exists. Build seeding first; don't add a role-protected endpoint before then.
- **No rate limiting exists yet on any auth endpoint.** `/register`, `/login`, `/refresh`, and `/logout` are all currently unthrottled and anonymous — see `Architecture.md`'s "Known limitations" and `project-journal.md` for tracking. `/me` is unthrottled too, but `[Authorize]` means an attacker must already hold a validly-signed token to reach it, so it is not exposed on the same terms.

## Notes for future developers (and future Claude Code sessions) on the frontend

- **Never decode the JWT on the frontend.** `/me` is the only source of current-user truth (see "The endpoint is database-backed by deliberate choice" above) — a frontend that reads claims off the access token instead would reintroduce exactly the staleness `/me` exists to close, and would break silently the first time a claim shape changes server-side.
- **Never store the access token anywhere JS-persistent.** It lives in a module variable (`frontend/src/lib/api/tokenStore.ts`), not `localStorage`/`sessionStorage`/React state. This is deliberate, not an oversight to "fix" by adding persistence — see `Architecture.md` → "Frontend" → "Access-token storage" for the full reasoning, including the explicit acknowledgment that this does not make the app XSS-safe by itself.
- **The single-flight refresh in `frontend/src/lib/api/client.ts` is not incidental — it is the client-side fix `Architecture.md`'s "Known limitations" section explicitly asks for** ("The primary fix for both triggers belongs on the client: single-flight the refresh call"). Do not replace `refreshAccessToken()`'s shared in-flight promise with a naive per-call `fetch` — that reopens the parallel-refresh self-lockout the backend documents.
- **Register has two distinct 400 response shapes, and code that assumes only one will break silently on the other:** `[ApiController]` model validation returns `ValidationProblemDetails` (`{ errors: { "Email": [...] } }`), while `BadRequest(result.Errors)` (Identity/uniqueness failures) returns a **bare JSON string array** (`["Email 'x' is already taken."]`). `frontend/src/lib/api/errors.ts`'s `toApiError` handles both — extend it, don't bypass it, if a new endpoint introduces a third shape.
- **The server password policy is stricter than `RegisterRequest`'s `[MinLength(8)]` alone suggests.** `AddIdentityCore` (`Infrastructure/DependencyInjection.cs`) also requires a digit, a lowercase letter, an uppercase letter, and a symbol. The frontend's `getPasswordRequirements` (`frontend/src/features/auth/validation.ts`) mirrors this exactly — if the backend policy ever changes, that function is the one place to update, and it should be updated in the same change, not discovered later via a confusing 400.
- **Two backend responses return `401` with an empty body** — the JWT bearer middleware's own 401 (no token, expired token, bad signature), as opposed to the JSON `{ message }` shape `AuthController`'s own actions return. `toApiError` does not assume a JSON body is present; don't reintroduce that assumption in new error-handling code.
- **`frontend/vite.config.ts` proxies `/api` to the backend instead of the backend exposing CORS.** No CORS policy exists on `Program.cs` for this milestone — see `Architecture.md` → "Frontend" → "CORS / dev proxy" for why, and for the explicit gap this leaves (no non-proxied deployment path exists yet).
- **`Products`/`Orders` in `AppLayout`'s nav are inert placeholders** ("Soon" badge, `aria-disabled`, no route) — there is no `features/products` or `features/orders` folder yet. Don't build against nav items that don't route anywhere; that is intentional for this milestone, not a bug to silently "fix" by adding a route.

## Notes for future developers (and future Claude Code sessions) on the product catalogue

- **`Product`, `ProductAttributeValue`, and `ProductImage` exist in the database and in `NimbusCommerce.Domain`, but still have no behavior.** `AttributeDefinition` and `CategoryAttributeDefinition` became behavior-complete in Sprint 4, Milestone 2 (see the two bullets below) — the remaining three entities' tables were created in the same Milestone 1 migration (`AddProductCatalog`) so the full six-table schema, including every foreign key between them, could be designed and validated together, rather than bolted on table-by-table. Each still-inert entity class has private setters, a private EF-only constructor, and a doc comment naming the milestone that adds its factory/mutators. **Don't add a service, store method, or controller action against any of them without first checking whether that milestone has actually landed** — the presence of a `DbSet<Product>` on `ApplicationDbContext` is not evidence that `Product` is usable yet.
- **`AttributeDefinition` has no `IsRequired` property, on purpose.** Requiredness is a property of the `CategoryAttributeDefinition` relationship, not the definition itself — the same attribute can be required in one category and optional in another. `CategoryAttributeDefinition.IsRequired` is set via `Category.AddAttributeConfiguration`/`SetAttributeRequired`, exposed through `POST`/`PUT /api/categories/{id}/attributes...`. Don't add `IsRequired` back onto `AttributeDefinition`.
- **`AttributeDefinition.DataType` is immutable after creation, on purpose.** `Rename` changes `Name` only — there is no `ChangeDataType` mutator, and `UpdateAttributeDefinitionRequest` has no `DataType` field. Once `Product`/`ProductAttributeValue` exist, changing a definition's type has no sane migration story for already-stored values; this was decided up front rather than left to be discovered as a bug later. Don't add a way to change it without re-opening that discussion explicitly.
- **Category/AttributeDefinition association mutations go through `Category`, never through a standalone `CategoryAttributeDefinition` service.** `Category.AddAttributeConfiguration`/`SetAttributeRequired`/`RemoveAttributeConfiguration` are the only entry points; `CategoryAttributeDefinition.Create`/`SetRequired` are `internal`, callable only from `Category` in the same assembly. This follows `Architecture.md`'s own Milestone 1 statement that the join "is part of the `Category` aggregate" — don't introduce an `ICategoryAttributeDefinitionStore` or a parallel service that bypasses `Category` to mutate the join table directly.
- **A `[Required]` attribute on a non-nullable value-type request field (e.g. `Guid`) does not reject a missing field.** `[ApiController]` model validation only catches this if the property is nullable (`Guid?`) — a plain `Guid` silently binds a missing/omitted JSON field to `Guid.Empty` and validation passes. `AddCategoryAttributeRequest.AttributeDefinitionId` is `Guid?` for exactly this reason (caught in Milestone 2's own review, before the milestone was considered done). Follow this pattern for any future required `Guid`/`int`/`bool`/etc. request field — make it nullable, not the non-nullable primitive.
- **A store method may filter by a foreign id alone, without re-filtering by `OwnerUserId`, only when that id was already proven to belong to the caller earlier in the same use case.** `AttributeDefinitionStore.CountCategoryAssociationsAsync` counts `CategoryAttributeDefinitions` by `AttributeDefinitionId` alone — safe because `DeleteAttributeDefinitionService` already resolved that id through an owner-filtered `FindByIdAsync` before the count runs. Don't generalize this to a method whose id parameter arrives directly from caller input without a prior ownership-proving lookup — that would reopen the cross-tenant leak the ownership-filtering rule exists to prevent.
- **`ICurrentUser` is not `ICurrentUserService`, and this is the second time this document has to say so.** `ICurrentUserService` (`Application/Authentication/CurrentUser`) is still the `GET /api/auth/me` use case — unchanged, not renamed, not repurposed. `ICurrentUser` (`Application/Common/Interfaces/ICurrentUser.cs`) is the new ambient "who is calling right now?" accessor this document previously said to introduce "at the second authenticated use case" — the six Category use cases were that trigger. If a future catalogue use case needs the caller's id, inject `ICurrentUser` and call `RequireUserId()`; do not thread a `userId` parameter through by hand the way `AuthController` still does for its own actions, and do not reach for `ICurrentUserService`.
- **`CurrentUser` (`Infrastructure/Identity/CurrentUser.cs`) reads `ClaimTypes.NameIdentifier`, not `JwtRegisteredClaimNames.Sub` — same trap, third place it's now guarded against.** `AuthController.Me()`'s comment already explains why (`MapInboundClaims` rewrites `sub` before the principal arrives); `CurrentUser.UserId` repeats the same read for the same reason. If a fourth consumer of the claim ever needs to exist, it should call through `ICurrentUser`, not add a fourth hand-written `FindFirstValue(ClaimTypes.NameIdentifier)`.
- **Catalogue child entities (`CategoryAttributeDefinition`, `ProductAttributeValue`, `ProductImage`) have no `OwnerUserId` column.** They are only safe to load through a parent that has already been filtered by `OwnerUserId` — see the new rule in `coding-standards.md`, "Catalogue ownership filtering." Don't write a store method that queries one of these tables directly without joining through an owner-checked parent; that reintroduces the cross-tenant leak the missing column relies on the parent to prevent.
- **A category lookup for a category that belongs to another user returns `404`, not `403`.** `ICategoryStore.FindByIdAsync`/`GetDetailAsync` filter by `OwnerUserId` as part of the query itself, so another user's category simply doesn't match — there is no separate authorization check to remember to add. Keep this shape for every future catalogue lookup; a `403` here would let a caller distinguish "not yours" from "doesn't exist."
- **Category name uniqueness is enforced by a pre-check plus a database unique index, not by catching `DbUpdateException`.** `CreateCategoryService`/`UpdateCategoryService` call `ICategoryStore.ExistsWithNameAsync` for a clear `409` message; the `(OwnerUserId, Name)` unique index is the actual guarantee. Catching the EF exception in Application was deliberately rejected — Application has no `Microsoft.EntityFrameworkCore` package reference, and it should stay that way. If a future milestone (e.g. Products' SKU uniqueness) needs a tighter race guarantee than a pre-check, that decision needs to be made explicitly, not solved by quietly adding an EF reference to Application.
- **`OperationResult`/`OperationResult<T>` is for new catalogue use cases. Don't refactor `IdentityOperationResult`, `LoginResult`, or `RefreshResult` onto it as a "consistency" cleanup.** That was discussed and explicitly deferred — see `Architecture.md`, "Product Catalogue" → "`OperationResult`: an intentional evolution, scoped to new work only." Authentication's result types have their own documented properties (e.g. `LoginResult.Failure()`'s detail-free factory for enumeration-safety) that a mechanical refactor could accidentally weaken.
- **`PagedQuery` rejects out-of-range page sizes; it does not clamp them.** `pageSize=500` is a `400`, not a silently-substituted `pageSize=100`. If a future list endpoint's UI wants a friendlier client-side experience, that's a frontend concern (validate before sending); don't change the backend to clamp instead of reject — that was a deliberate choice made in review, not a default.
- **No test project existed anywhere in this repository before this milestone.** `backend/tests/NimbusCommerce.UnitTests` (xUnit) now exists, scoped deliberately narrow: pure Domain/Application logic only (`Category`'s entity mutators, `PagedResult.TotalPages`) — no database, no `WebApplicationFactory`, no mocking framework. Rules that need a database query to evaluate (e.g. "cannot deactivate a category with active products") are **not** unit-testable this way and are verified by the manual end-to-end procedure instead; don't try to force them into this project with a mocked store, since that would mostly be testing the mock.
